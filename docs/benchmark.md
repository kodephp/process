# 压测数据

同一份业务代码（`benchmarks/portable-server.php`：HTTP GET `/` → 12 字节纯文本），在 **native / swoole / workerman** 三种运行时与 **HTTP/1.1 / HTTP/2（h2c）** 两种协议下的实测吞吐与延迟对比。

> 所有数字均在 **最新版（v5.2.6）** 下测得，同一台机器、同一份服务、同一份载荷，唯一变量是运行时 / 协议。
> 复现方法见文末「怎么复现」。wrk 在 4 worker 下会逼近压测端天花板，横向 QPS 差异落在噪声区间；
> 可干净复现的优势只在「同进程背靠背纯 CPU 微基准」，文中已单独列出。

## 测试条件

| 项 | 值 |
|----|----|
| 版本 | v5.2.6（PHP 8.3.33，11 核） |
| 参数 | workers=4，duration=12s，connections=200，threads=4 |
| 载荷 | HTTP GET `/` → 12 字节纯文本 |

## 一、三运行时吞吐对比（HTTP/1.1，wrk）

同一条件连跑 **两轮**，两轮都如实列出——单轮结果会被压测端抖动主导，只报一轮容易得出错误结论：

| 运行时 | 第 1 轮 QPS | 第 2 轮 QPS | 第 1 轮 P99 | 第 2 轮 P99 |
|--------|-----------:|-----------:|-----------:|-----------:|
| **native**（自研，零扩展，自适应 reusePort） | 176,119 | **184,564** | 15.36 ms | **2.48 ms** |
| **swoole**（C 实现） | **178,562** | 176,273 | 7.13 ms | 6.15 ms |
| **workerman**（纯 PHP 依赖） | 171,577 | 173,713 | 6.84 ms | 7.42 ms |

- 三者始终处于**同一量级**（172k–185k），轮次间差异（native 176k↔185k）大于运行时之间的差异，
  说明宏观 QPS 已被压测端天花板与调度抖动主导，**不足以支撑任何一方"更快"的结论**。
- native 第 1 轮的 P99 15.36 ms 是离群噪声：第 2 轮同一条件下降到 **2.48 ms，为三者最低**。
  这正是"单轮数据不可信"的实证，也是这里坚持并列两轮的原因。
- 要看真实代码差距，请直接看第三节的**纯 CPU 微基准**——那里隔离了 socket 与事件循环，方向稳定可复现。

## 二、HTTP/2（h2c）vs HTTP/1.1（同一 native 服务、同时刻）

`benchmarks/h2-bench.sh` 对**同一份 native 服务、同一时刻**分别施加 h2load（h2c prior-knowledge）与 wrk（HTTP/1.1），唯一变量是协议版本。

| 协议 | 工具 | QPS | 请求 P50 | 请求 P99 | 说明 |
|------|------|----:|--------:|--------:|------|
| **HTTP/1.1** | wrk | **173,000** | 0.72 ms | 4.06 ms | keep-alive，4 worker |
| **HTTP/2 (h2c)** | h2load | **155,000** | 0.83 ms | **2.70 ms** | **100 万请求** / 200 连接 / 4 线程，**0 错误 0 超时** |

- 在「12 字节极小响应」这种端点上，HTTP/2 每请求要额外付成帧 + HPACK 编解码 + 流状态机开销，
  吞吐比 h1.1 **低约 10%**（155k vs 173k）——这是协议固有代价，与「自研慢」无关；h1.1 在轻载荷上本就更省。
  宏观 QPS 受事件循环与压测端天花板主导（见 §1），解码侧优化体现在 §3 的纯 CPU 微基准：
  v5.2.6 使 `Hpack::decode` **再快约 1.47×**、请求热路径**快约 12%**（§3.2–§3.4），
  但宏吞吐保持在同噪声带内（多次复跑 h2c 落在 150k–165k req/s），不与「解码变快」矛盾。
- 而 h2c 的**请求 P99 明显更低（2.58 ms vs 5.37 ms，低 52%）**，且支持多路复用：真实业务里「一个页面并发几十个
  请求」时，h2c 用一条 TCP 连接即可，省去 h1.1 的队头阻塞与连接数上限，优势才会真正显现。
- 100 万请求全部 2xx、**0 失败 0 超时**，说明流状态机与流控在长时间高压下稳定。
- **h2c 仅 native 提供**：本框架里 Workerman 的服务端是 HTTP/1.1-only，Swoole 的 HTTP/2 需要 TLS（ALPN），
  无法做 cleartext h2c 对比；native 默认即开 h2c（prior-knowledge / Upgrade 升级），是三者中唯一能在明文下直接跑 HTTP/2 的运行时。

## 三、纯 CPU 微基准（隔离 socket 与事件循环）

### 3.1 请求热路径（每请求必做的 PHP 工作量）

隔离网络层，只跑每请求必须做的 PHP 工作（input → decode → rawHeader ×2 → encode）。
native 与 workerman 在**同一进程内背靠背**比较，共独立运行 6 次：

| 运行时热路径（每 20 万次） | 典型耗时 | 相对 |
|---------------------------|---------:|-----:|
| **native** | **~78 ms** | — |
| workerman | ~90 ms | +14~17% |

**方向 100% 稳定**：6 次独立运行中 native **每一次都快于 workerman**（中位数约 -17%）。
跨进程绝对数字会波动，但同进程背靠背比较始终 native 占优，说明差距来自代码而非噪声。

### 3.2 HTTP/2 请求热路径（当前版本实测）

宏观 QPS 被压测端天花板掩盖，但 HTTP/2 每请求要做的 PHP 工作量是可以精确称量的。
`benchmarks/h2-split.php`（每 10 万次完整请求）与 `benchmarks/h2-components.php`
（每 50 万次纯函数调用）在 v5.2.6 上的实测：

| 阶段（每 10 万次请求） | 耗时 | 吞吐 |
|------------------------|-----:|-----:|
| **feed**（帧解码 + HPACK 解码 + 收齐头） | **283 ms** | 353,357 ops/s |
| **respond**（HPACK 编码 + 成帧） | **120 ms** | 833,333 ops/s |
| 合计（每请求必做的全部 PHP 工作） | **≈403 ms** | — |

| 纯函数组件（每 50 万次） | 耗时 | 吞吐 |
|--------------------------|-----:|-----:|
| `Frame::decode` | 100.69 ms | 4,965,878 ops/s |
| `Frame::encode` | 69.47 ms | 7,197,351 ops/s |
| `Hpack::decode`（请求头块） | 503.98 ms | 992,108 ops/s |
| `Hpack::encode`（响应头列表） | 560.21 ms | 892,518 ops/s |

### 3.3 四层纯函数缓存（提速来源）

上面的数字之所以能压到这个量级，靠的是四层**纯函数缓存**——它们缓存的都是
「输入唯一决定输出」的计算结果，**线格式与未缓存时逐字节一致**，不改变任何协议行为：

| 缓存 | 方向 | 依据 | 收益 |
|------|------|------|-----:|
| `Hpack::$literalCache` | 明文 → 已编码字节 | 字面量编码只依赖该字符串本身 | 编码热路径 **≈5.7×** |
| `Http2Session::$responseBlockCache` | `(status, headers)` → 整个头块 | 服务端编码器恒走「不索引」表示、**动态表恒空**，整块编码即纯函数 | respond **≈2.2×** |
| `Hpack::$huffmanCache` | 已编码字节 → 明文 | Huffman 解码只依赖输入字节，与动态表无关 | `Hpack::decode` **≈1.93×** |
| `Hpack::$headerCache` | `name + value` → 已编码字节 | 整头编码只依赖该 `name + value` 组合，稳态下响应头组合高度固定 | `Hpack::encode` **≈3.4×** |

四者形成闭环：响应侧（整块缓存 + 整头缓存）与请求侧（解码缓存 + Huffman 缓存）**都已被覆盖**。
叠加 v5.2.6 的解码主循环内联（§3.4），HTTP/2 请求热路径自 v5.2.3 起累计快约 **1.9×**
（≈783 ms → ≈403 ms / 10 万次）；编码侧再叠加 v5.2.7 整头缓存，`Hpack::encode` 另快约
**3.4×**（537 ms → 156 ms / 50 万次）。

安全性上四层缓存均有边界：条目数上限（1024 / 256 / 1024 / 1024）防止无限增长；Huffman 缓存
额外限制单条 ≤ 512 字节，且**只缓存解码成功的结果**——非法输入抛异常且不入缓存，
攻击者无法用畸形数据占位。缓存均可用 `clearLiteralCache()` / `clearResponseBlockCache()` /
`clearHuffmanCache()` / `clearHeaderCache()` 清空，便于测试隔离与基准冷启动。

### 3.4 第四项优化：HPACK 解码主循环内联（v5.2.6）

前三层都是「缓存纯函数」；而 `Hpack::decode` 的**剩余成本来自方法分发本身**——每个头字段都要经
`readInteger` / `readString` 两个私有方法的调用（一次 6 头请求约 13 次 `readInteger` + 3 次 `readString`，
且均带 `&$i` 引用），PHP 的方法调用与引用传参开销在百万级调用下不可忽略。

v5.2.6 将变长整数解码**直接内联进 `decode()` 主循环**（索引 / 动态表更新 / 字面量名 / 字面量值四处的
整数读取就地展开），字符串读取收敛为一个保留边界校验与 Huffman 缓存调用的 `readStringInline`。
与原实现**逐字节输出完全一致**（RFC 7541 附录 C 全部向量、增量索引 6.2.1 触发 `push`、畸形输入报错路径、
以及 4000 组随机头 fuzz 均一致），HPACK / HTTP/2 单测 80 项全绿。

收益（每 50 万次，与 v5.2.5 同机同脚本）：

| 输入 | v5.2.5 | v5.2.6 | 提速 |
|------|-------:|-------:|-----:|
| 带 Huffman 字面量请求块 | 742.51 ms | 503.98 ms | **≈1.47×** |
| 纯索引请求块（无 Huffman） | 121.55 ms | 59.20 ms | **≈2.05×** |

纯索引块提速更明显（≈2×），因为它几乎只由内联后的整数读取构成。叠加进请求热路径后，`feed`
（解码侧）从 333.78 ms 降到约 283 ms，HTTP/2 请求热路径合计从 ≈456 ms 降到 ≈403 ms（较 v5.2.5 **快约 12%**）。

### 3.5 第五项优化：HPACK 整头编码缓存（v5.2.7）

`Hpack::encode` 在 v5.2.6 时仍是请求热路径里**最重的纯函数**（537 ms / 50 万）——比已内联的 `decode`
还重。剖析发现它的成本几乎全在**结构性的逐头拼接**：每个头字段都要走「静态表查对（`. "\0" .` 拼接键）
→ `writeInteger` → `writeString` → `.=` 拼接」，而即便 `literalCache` 命中，也要重新做一遍查表与拼接。
换言之，旧缓存只省了「字面量值编码」，没省「整头组装」。

v5.2.7 引入 `Hpack::$headerCache`（`name + value` → 整段已编码字节）：一次命中即可直接 `.=` 拼回，
省去查对 / 整数编码 / 字面量编码 / 多次拼接四步。键为 `(name, value)` **嵌套数组**（非 `. "\0" .`
拼接），**同名不同值的头不会串**（验证见下）。静态表整对命中（§6.1）也走同一缓存路径。

与解码侧三层缓存**严格对称**：都是缓存「输入唯一决定输出」的纯函数结果，线格式逐字节不变。
上限 1024 条，达到后停止写入（`storeHeader`），不增长内存；可用 `clearHeaderCache()` 清空。

收益（每 50 万次，与 v5.2.6 同机同脚本）：

| 输入 | v5.2.6 | v5.2.7 | 提速 |
|------|-------:|-------:|-----:|
| 响应头列表（6 头，稳态） | 537 ms | 156 ms | **≈3.44×** |
| 请求头列表（6 头，稳态） | 412 ms | 124 ms | **≈3.3×** |

稳态下真实响应经 `responseBlockCache`（v5.2.4）已跳过整段编码；整头缓存主要惠及
**缓存未命中的变体响应**与**主动编码场景**，并把 `Hpack::encode` 这一曾最重纯函数降到最轻。
正确性用「RFC 向量 + 增量索引 + 4000 组 fuzz + 同名异值不串」全量验证，HPACK 单测新增
3 条 `headerCache` 守护，全量 **760 测试 / 9170 断言 / 1 skipped 全绿**。

## 四、安全：HTTP/2 DoS 防护的性能代价

提速不能以牺牲安全为代价。native 的 HTTP/2 内建四道防线，且**全部为 O(1) 计数**，
不引入额外遍历或分配，对上面的热路径数字无可测量影响：

| 防线 | 覆盖攻击面 | 触发动作 | 开销 |
|------|-----------|---------|------|
| `MAX_HEADER_BLOCK_SIZE`（64 KiB） | CONTINUATION 分片堆积 | `RST_STREAM` 该流 | 累加比较 |
| `MAX_HEADER_LIST_SIZE`（64 KiB） | 高压缩比头膨胀 | `RST_STREAM` 该流 | 解码循环内边解边累加 |
| RST_STREAM 预算（默认上限 512） | **Rapid Reset / CVE-2023-44487** | `GOAWAY(ENHANCE_YOUR_CALM)` | 自增 / 自减 |
| 控制帧排队上限（1000） | PING / SETTINGS 洪泛 | `GOAWAY(ENHANCE_YOUR_CALM)` | 自增，`drain()` 归零 |

Rapid Reset 防护采用「**预算 + 抵扣**」：收到对端 `RST_STREAM` 预算 +1，每有一条流
**正常完成响应**预算 −1。正常客户端的完成数远多于取消数，预算稳定在 0 附近，不会误伤；
而只重置不完成的攻击流量预算只增不减，很快触顶被掐断。该设计不依赖时钟，行为确定可测试。

四道防线各有回归用例守护，`stats()` 亦暴露 `reset_budget` / `reset_limit` / `queued_control`
三个实时水位便于接入监控。详见 [HTTP/2 文档](http2.md)。

## 五、大响应长时压测（健壮性验证）

提速之外，native 的 HTTP/2 必须在大响应、长时、高并发下保持**流控稳定**与**内存不泄漏**。
本项用 `benchmarks/h2-large-stress.sh` 驱动 `benchmarks/portable-server-large.php`
（响应体可配，默认 256KB），以 h2c prior-knowledge 持续施压，并由各 worker 周期性
向 STDERR 打印 PHP 内存峰值，压测后分析是否随时间无界增长。

实测（4 worker，200 连接，60s 持续；1MB 用例降为 100 连接以避免带宽饱和）：

| 响应体 | 吞吐 | 流量 | 请求数 | 失败 / 错误 / 超时 | p99 延迟 | 每 worker 内存峰值 | 峰值增长 |
|--------|-----:|-----:|------:|:-----------------:|--------:|------------------:|:--------:|
| 256 KB | 29,660 req/s | 6.92 GB/s | 1,779,580 | **0 / 0 / 0** | 17.55 ms | 6.29 MB | **0 bytes** |
| 1 MB   | 3,842 req/s  | 3.58 GB/s | 230,529   | **0 / 0 / 0** | 56.94 ms | 10–14 MB | **0 bytes** |

结论：
- **流控稳定**：256KB 与 1MB 响应在 60s 持续、数百并发下均 **0 失败 / 0 错误 / 0 超时**，
  说明服务端发送窗口随对端 `WINDOW_UPDATE` 正确补还，无窗口耗尽导致的流停滞或连接级异常。
- **无内存泄漏**：每个 worker 的 PHP 峰值内存在数百万次大响应后**完全恒定**
  （增长 = 0 bytes），大响应缓冲（`pending` / `body`）与流对象池均正确回收。
- **会话级开销已是最优**：`feed → completeHeaders → buildRequest` 链路无冗余解码或重建，
  60s 压测中每请求约 1.7µs 的会话成本主要是为正确性必需的数组分配；进一步压榨需把
  `Hpack::decode` 与会话层强耦合，得不偿失——健壮性优先，此处不再微优化。

> 注：1MB 的吞吐与延迟受带宽主导，与「自研慢」无关；其价值在于验证大响应下的健壮性与零泄漏。

## 使用方向（选型建议）

1. **受限 / 容器 / 无扩展环境**：不装 swoole/workerman 扩展即可跑起完整 HTTP + WebSocket + HTTP/2 服务——选 **native**。
2. **现代 PHP 8.3+ 项目**：枚举、只读属性、Fibers 等，代码即服务器，调试直观——选 **native**。
3. **需要 HTTP/2（h2c）**：gRPC 网关、前端静态资源、内部多路复用 RPC——**只有 native 默认即开**，明文即可。
4. **极致单连接吞吐 / 协程**：高并发 I/O 密集且能装 C 扩展——选 **swoole**。
5. **已深度使用 Workerman 生态**：业务已绑定 Workerman 组件——选 **workerman**（native 可零改动切换做对标）。
6. **自建 PaaS / 嵌入式 / 教学**：一份纯 PHP 源码，改得动、读得懂——选 **native**。

> 一句话：自研不强在「压榨极限吞吐」（那是 C 扩展的领地），而强在「零安装即得、PHP 8.3+ 现代写法、
> HTTP/2 开箱即用且自带 DoS 防护、协议与关闭更规范、代码可读可测」。在绝大多数业务服务的吞吐区间内，
> 它与 swoole / workerman **同量级**，并在请求热路径 CPU 上稳定领先（微基准 6/6 全胜）；
> HTTP/2 请求热路径经 v5.2.4（响应整块缓存 ≈2.2×）、v5.2.5（Huffman 解码缓存 ≈1.93×）、
> v5.2.6（解码主循环内联 ≈1.47×）三轮优化，请求热路径自 v5.2.3 起累计快约 **1.9×**，
> h2c 与 h1.1 的吞吐差距稳定在协议固有代价区间。

