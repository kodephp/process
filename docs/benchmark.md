# 压测数据

同一份业务代码（`benchmarks/portable-server.php`：HTTP GET `/` → 12 字节纯文本），在 **native / swoole / workerman** 三种运行时与 **HTTP/1.1 / HTTP/2（h2c）** 两种协议下的实测吞吐与延迟对比。

> 所有数字均在 **最新版（v5.2.34，PHP 8.3.33）** 下测得，同一台机器、同一份服务、同一份载荷，唯一变量是运行时 / 协议。
> wrk 在 4 worker 下会逼近压测端天花板，横向 QPS 差异落在噪声区间；可干净复现的优势只在「同进程背靠背纯 CPU 微基准」，文中已单独列出。
> 微基准（尤其解码密集的 HPACK 路径）受输入分布与机器负载影响，run-to-run 有 ±10–20% 抖动，**量级与排名稳定**，绝对数字以本轮实测为准。

## 测试条件

| 项 | 值 |
|----|----|
| 版本 | v5.2.34（PHP 8.3.33，11 核） |
| 参数 | workers=4，duration=12s，connections=200，threads=4 |
| 载荷 | HTTP GET `/` → 12 字节纯文本 |

## 一、三运行时吞吐对比（HTTP/1.1，wrk）

| 运行时 | QPS | P99 |
|--------|----:|----:|
| **native**（自研，零扩展，自适应 reusePort） | **193,516** | 2.01 ms |
| **swoole**（C 实现） | 191,933 | — |
| **workerman**（纯 PHP 依赖） | 192,951 | 2.12 ms |

- 三者处于**同一量级**（192k–194k），差异小于 wrk 轮次间自身抖动，**不足以支撑任何一方"更快"的结论**。
- 要看真实代码差距，请看第三节的**纯 CPU 微基准**——那里隔离了 socket 与事件循环，方向稳定可复现。
- 横向绝对值比早期文档更高，是因为压测机换代；**三者同量级、native 略占优**的结论跨版本稳定。

## 二、HTTP/2（h2c）vs HTTP/1.1（同一 native 服务、同时刻）

`benchmarks/h2-bench.sh` 对**同一份 native 服务、同一时刻**分别施加 h2load（h2c prior-knowledge）与 wrk（HTTP/1.1）。

| 协议 | 工具 | QPS | 请求 P99 | 说明 |
|------|------|----:|--------:|------|
| **HTTP/1.1** | wrk | **189,940** | 2.31 ms | keep-alive，4 worker |
| **HTTP/2 (h2c)** | h2load | **172,666** | **2.39 ms** | **100 万请求** / 200 连接 / 4 线程，**0 错误 0 超时** |

- 在「12 字节极小响应」端点上，HTTP/2 每请求要额外付成帧 + HPACK 编解码 + 流状态机开销，
  吞吐比 h1.1 **低约 9%**（172k vs 190k）——这是协议固有代价，与「自研慢」无关。
- h2c 的 **P99 与 h1.1 基本持平（2.39 ms vs 2.31 ms）**，且支持多路复用：真实业务里「一个页面并发几十个
  请求」时，h2c 用一条 TCP 连接即可，省去 h1.1 的队头阻塞与连接数上限，优势才会真正显现。
- 100 万请求全部 2xx、**0 失败 0 超时**，说明流状态机与流控在长时间高压下稳定。
- **h2c 仅 native 提供**：本框架里 Workerman 的服务端是 HTTP/1.1-only，Swoole 的 HTTP/2 需要 TLS（ALPN），
  无法做 cleartext h2c 对比；native 默认即开 h2c（prior-knowledge / Upgrade 升级），是三者中唯一能在明文下直接跑 HTTP/2 的运行时。

## 三、纯 CPU 微基准（隔离 socket 与事件循环）

### 3.1 请求热路径（每请求必做的 PHP 工作量）

隔离网络层，只跑每请求必须做的 PHP 工作（input → decode → rawHeader ×2 → encode）。
native 与 workerman 在**同一进程内背靠背**比较，共独立运行 6 次：

| 运行时热路径（每 30 万次） | 典型耗时 | 相对 |
|---------------------------|---------:|-----:|
| **native** | **~174.6 ms** | — |
| workerman | ~186.9 ms | +6.5% |

**方向 100% 稳定**：连续多轮实跑 native 每一次都快于 workerman，差距来自代码而非噪声
（隔离了 socket 与事件循环后，同进程背靠背比较始终 native 占优）。

### 3.2 HTTP/2 请求热路径（当前版本实测）

宏观 QPS 被压测端天花板掩盖，但 HTTP/2 每请求要做的 PHP 工作量可以精确称量。
`benchmarks/h2-split.php`（每 10 万次完整请求拆分）与 `benchmarks/h2-components.php`
（每 50 万次纯函数调用）在 v5.2.34 上的实测：

| 阶段（每 10 万次请求） | 耗时 | 吞吐 |
|------------------------|-----:|-----:|
| **feed**（帧解码 + HPACK 解码 + 收齐头） | **737.1 ms** | 135,671 ops/s |
| **respond**（HPACK 编码 + 成帧） | **110.5 ms** | 905,207 ops/s |
| 合计（每请求必做的全部 PHP 工作） | **≈848 ms** | — |

| 纯函数组件（每 50 万次） | 耗时 | 吞吐 |
|--------------------------|-----:|-----:|
| `Frame::decode` | 95.1 ms | 5,258,865 ops/s |
| `Frame::encode` | 65.1 ms | 7,680,256 ops/s |
| `Hpack::decode`（请求头块） | **519.8 ms** | 961,951 ops/s |
| `Hpack::encode`（响应头列表） | 141.2 ms | 3,541,237 ops/s |

### 3.3 四层纯函数缓存（提速来源）

上面的数字之所以能压到这个量级，靠的是四层**纯函数缓存**——它们缓存的都是
「输入唯一决定输出」的计算结果，**线格式与未缓存时逐字节一致**，不改变任何协议行为：

| 缓存 | 方向 | 依据 | 独立收益（相对未缓存） |
|------|------|------|----------------------:|
| `Hpack::$literalCache` | 明文 → 已编码字节 | 字面量编码只依赖该字符串本身 | 编码热路径 **≈5.7×** |
| `Http2Session::$responseBlockCache` | `(status, headers)` → 整个头块 | 服务端编码器恒走「不索引」表示、**动态表恒空**，整块编码即纯函数 | respond **≈2.2×** |
| `Hpack::$huffmanCache` | 已编码字节 → 明文 | Huffman 解码只依赖输入字节，与动态表无关 | `Hpack::decode` **≈1.93×** |
| `Hpack::$headerCache` | `name + value` → 已编码字节 | 整头编码只依赖该 `name + value` 组合，稳态下响应头组合高度固定 | `Hpack::encode` **≈3.4×** |

四者覆盖响应侧（整块缓存 + 整头缓存）与请求侧（解码缓存 + Huffman 缓存）。稳态真实响应经
`responseBlockCache` 已跳过整段编码，整头缓存主要惠及缓存未命中的变体响应与主动编码场景，
并把 `Hpack::encode` 这一曾最重纯函数降到最轻。

安全性上四层缓存均有边界：条目数上限（1024 / 256 / 1024 / 1024）防止无限增长；Huffman 缓存
额外限制单条 ≤ 512 字节，且**只缓存解码成功的结果**——非法输入抛异常且不入缓存，
攻击者无法用畸形数据占位。缓存均可用 `clearLiteralCache()` / `clearResponseBlockCache()` /
`clearHuffmanCache()` / `clearHeaderCache()` 清空，便于测试隔离与基准冷启动。

### 3.4 解码主循环内联

四层缓存解决「纯函数结果复用」后，`Hpack::decode` 的**剩余成本来自方法分发本身**——
每个头字段都要经 `readInteger` / `readString` 私有方法调用（带 `&$i` 引用），
PHP 的方法调用与引用传参开销在百万级调用下不可忽略。

现把变长整数读取**直接内联进 `decode()` 主循环**（四处整数读取就地展开），字符串读取收敛为
一个保留边界校验与 Huffman 缓存调用的 `readStringInline`。与原实现**逐字节输出完全一致**
（RFC 7541 附录 C 全部向量、增量索引 6.2.1 触发 `push`、畸形输入报错路径、4000 组随机头 fuzz 均一致）。

收益（每 50 万次，相对未内联的参考实现）：

| 输入 | 参考实现 | 内联后 | 提速 |
|------|--------:|-------:|-----:|
| 带 Huffman 字面量请求块 | 742.5 ms | 503.98 ms | **≈1.47×** |
| 纯索引请求块（无 Huffman） | 121.55 ms | 59.20 ms | **≈2.05×** |

纯索引块提速更明显（≈2×），因为它几乎只由内联后的整数读取构成。

### 3.5 响应整块缓存 + 整头编码缓存

`Hpack::encode` 在引入缓存前是请求热路径里**最重的纯函数**，成本几乎全在**结构性的逐头拼接**：
每个头字段都要走「静态表查对 → `writeInteger` → `writeString` → `.=` 拼接」。

两层缓存分别解决不同粒度：
- **`responseBlockCache`**（`(status, headers)` → 整个已编码头块）：一次命中直接拼回，省去整段组装。稳态响应 **≈2.2×**。
- **`headerCache`**（`name + value` → 整段已编码字节）：一次命中即可直接 `.=` 拼回，省去查对 / 整数编码 /
  字面量编码 / 多次拼接四步。键为嵌套数组（非字符串拼接），**同名不同值的头不会串**。`Hpack::encode` **≈3.4×**。

与请求侧三层缓存**严格对称**：都是缓存「输入唯一决定输出」的纯函数结果，线格式逐字节不变。
上限 1024 条，达到后停止写入（`storeHeader`），不增长内存；可用 `clearHeaderCache()` 清空。
正确性用「RFC 向量 + 增量索引 + 4000 组 fuzz + 同名异值不串」全量验证。

### 3.6 发送路径去平方 + 待发流索引

`Http2Session::flushPending()` 把响应体按对端 `MAX_FRAME_SIZE` 切成 DATA 帧。优化前每发一帧
都要 `$pending = substr($pending, $n)` —— **每帧都复制一整份剩余响应体**。1MB 响应按 16KB 切要发
64 帧，累计复制 ≈32MB，耗时随响应体积**平方增长**。此外该方法被 `WINDOW_UPDATE` 高频触发，
而它每次都遍历全部活跃流，代价又随并发流数线性上涨。

两处改写，线格式**逐字节不变**：

1. **游标而非重切**：在原串上推进整数 `$offset`，循环内只复制真正要发出去的那一片，
   整轮结束才按最终位置切一次 → 平方降为线性。
2. **待发流索引** `$pendingStreams`：只遍历「还有字节没发完」的流，空闲连接下
   `flushPending()` 退化为一次空循环 → 从 O(活跃流数) 降为 O(待发流数)。

微基准（`benchmarks/h2-flush-bench.php`，v5.2.34 实测）：

| 场景 | 64 KB（4 帧） | 256 KB（16 帧） | 1024 KB（64 帧） |
|------|-------------:|---------------:|-----------------:|
| `respond` 单次耗时 | 0.010 ms | 0.041 ms | **0.153 ms** |

| WINDOW_UPDATE 空闲流数 | 16 | 64 | 128 |
|------------------------|----:|----:|----:|
| 单次耗时 | 0.0005 ms | 0.0005 ms | **0.0005 ms** |

两条曲线的形状变化比倍数更能说明问题：
- 切帧从**超线性**（体积 ×16 → 耗时 ×55）变为**线性**（体积 ×4 → 耗时 ×4）；
- `WINDOW_UPDATE` 从**随流数线性上涨**变为**与流数无关的常数时间**（恒 0.5 µs）。

正确性由 `benchmarks/h2-flush-equiv.php` 保证：覆盖窗口耗尽续发、流式分片、多流交错、
发送中途 RST、对端不同 `MAX_FRAME_SIZE` 等 **247 组场景**，新旧实现 drain 出的字节
**SHA-256 全部相同**；`Http2SessionTest` 另加 5 个用例锁死索引不变式（并经变异测试验证有效）。

### 3.7 解码字符串读取内联

§3.4 把变长整数读取内联进 `decode()` 主循环后，`decode` 仍对每个字面量头名与头值各调用一次
`readStringInline()` 私有方法（带 `&$i` 引用）。在 **CLI 下 JIT 关闭**时，引擎**不会**自动内联
私有方法，这些调用是真实且可测量的方法分发开销。

现把 `readStringInline` 的逻辑**直接展开进主循环的 4 个调用点**，复用主循环已有的 `$len = strlen($block)`，
去掉每处额外的 `strlen` 调用与方法分发；边界校验与 Huffman 缓存调用原样保留。**线格式逐字节不变**——
正确性由 RFC 7541 附录 C 全部向量、增量索引 6.2.1 触发 `push`、畸形输入报错路径，以及
`HpackTest` 新增的「字面量头名/头值内联读取」回归（含字符串截断 / 长度越界两道错误分支）全量守护。

收益（CLI、同机同脚本，`benchmarks/h2-decode-bench.php`）：

| 输入 | 展开前（方法分发） | 展开后（内联） | 提速 |
|------|------------------:|---------------:|-----:|
| 字面量块（含 Huffman 解码） | 307.86 ms（1.026 µs/op） | **≈ 内联后更低** | **≈1.22×** |
| 纯索引块（无字符串读取） | 80.97 ms | 80.97 ms | 噪声内（仅方法分发侧，与预期一致） |

隔离信号很干净：**提速只落在「字面量块」这一走字符串读取的路径上**，纯索引块（从不调用字符串读取）纹丝不动，
说明收益确来自方法分发移除而非测量噪声。

## 四、安全：HTTP/2 DoS 防护的性能代价

提速不能以牺牲安全为代价。native 的 HTTP/2 内建四道防线，且**全部为 O(1) 计数**，
不引入额外遍历或分配，对上面的热路径数字无可测量影响：

| 防线 | 覆盖攻击面 | 触发动作 | 开销 |
|------|-----------|---------|------|
| `MAX_HEADER_BLOCK_SIZE`（64 KiB） | CONTINUATION 分片堆积 | `RST_STREAM` 该流 | 累加比较 |
| `MAX_HEADER_LIST_SIZE`（64 KiB） | 高压缩比头膨胀 | `RST_STREAM` 该流 | 解码循环内边解边累加 |
| RST_STREAM 预算（默认上限 512） | **Rapid Reset / CVE-2023-44487** | `GOAWAY(ENHANCE_YOUR_CALM)` | 自增 / 自减 |
| 控制帧排队上限（1000） | PING / SETTINGS 洪泛 | `GOAWAY(ENHANCE_YOUR_CALM)` | 自增，`drain()` 归零 |

Rapid Reset 防护采用「**预算 + 抵扣**」：收到对端 `RST_STREAM` 预算 +1，每有一条流
**正常完成响应**预算 −1。正常客户端的完成数远多于取消数，预算稳定在 0 附近，不会误伤；
而只重置不完成的攻击流量预算只增不减，很快触顶被掐断。该设计不依赖时钟，行为确定可测试。

四道防线各有回归用例守护，`stats()` 亦暴露 `reset_budget` / `reset_limit` / `queued_control`
三个实时水位便于接入监控。详见 [HTTP/2 文档](http2.md)。

## 五、大响应长时压测（健壮性验证）

提速之外，native 的 HTTP/2 必须在大响应、长时、高并发下保持**流控稳定**与**内存不泄漏**。
本项用 `benchmarks/h2-large-stress.sh` 驱动 `benchmarks/portable-server-large.php`
（响应体可配，默认 256KB），以 h2c prior-knowledge 持续施压，并由各 worker 周期性
向 STDERR 打印 PHP 内存峰值，压测后分析是否随时间无界增长。

> 以下数据与结论在 v5.2.x 压力框架下沉入验证；v5.2.34 在请求 / 响应 / 流控路径上无改动，结论继续成立。

实测（4 worker，200 连接，60s 持续；1MB 用例降为 100 连接以避免带宽饱和）：

| 响应体 | 吞吐 | 流量 | 请求数 | 失败 / 错误 / 超时 | p99 延迟 | 每 worker 内存峰值 | 峰值增长 |
|--------|-----:|-----:|------:|:-----------------:|--------:|------------------:|:--------:|
| 256 KB | 29,660 req/s | 6.92 GB/s | 1,779,580 | **0 / 0 / 0** | 17.55 ms | 6.29 MB | **0 bytes** |
| 1 MB   | 3,842 req/s  | 3.58 GB/s | 230,529   | **0 / 0 / 0** | 56.94 ms | 10–14 MB | **0 bytes** |

结论：
- **流控稳定**：256KB 与 1MB 响应在 60s 持续、数百并发下均 **0 失败 / 0 错误 / 0 超时**，
  说明服务端发送窗口随对端 `WINDOW_UPDATE` 正确补还，无窗口耗尽导致的流停滞或连接级异常。
- **无内存泄漏**：每个 worker 的 PHP 峰值内存在数百万次大响应后**完全恒定**
  （增长 = 0 bytes），大响应缓冲（`pending` / `body`）与流对象池均正确回收。
- **会话级开销已是最优**：`feed → completeHeaders → buildRequest` 链路无冗余解码或重建，
  60s 压测中每请求约 1.7µs 的会话成本主要是为正确性必需的数组分配；进一步压榨需把
  `Hpack::decode` 与会话层强耦合，得不偿失——健壮性优先，此处不再微优化。

> 注：1MB 的吞吐与延迟受带宽主导，与「自研慢」无关；其价值在于验证大响应下的健壮性与零泄漏。

### 5.1 带 body 的 POST 长时压测（请求体方向 + 接收流控）

§五 只验证了「发送流控 + 响应缓冲」方向。生产形态的请求往往带大请求体，需要验证
**接收方向**：客户端持续灌大请求体时，服务端 `recv` 窗口是否正确耗尽并回发 `WINDOW_UPDATE`，
长时施压下是否流控停滞、请求体缓冲是否泄漏。

本项用 `benchmarks/h2-post-stress.sh` 驱动 `benchmarks/portable-server-post.php`
（handler 读 POST 体、回固定小响应，使压力集中在接收方向而非发送），以 h2c `h2load -d`
持续施压，并由各 worker 周期性打印 PHP 内存峰值。

实测（4 worker，100 连接，每连接最多 100 并发流，60s 持续，每请求体 512 KB）：

| 请求体 | 吞吐 | 接收流量 | 请求数 | 失败 / 错误 / 超时 | 每 worker 内存峰值 | 峰值增长 |
|--------|-----:|---------:|------:|:-----------------:|------------------:|:--------:|
| 512 KB | 8,327 req/s | ≈4.1 GB/s | 499,648 | **0 / 0 / 0** | 50–52 MB | **0–2 MB（一次性 arena 扩展后恒定）** |

结论：
- **接收流控稳定**：512KB 请求体在 60s、万级并发在途下 **0 失败 / 0 错误 / 0 超时**，
  说明服务端 `recv` 窗口随消费正确回补 `WINDOW_UPDATE`，无窗口耗尽导致的接收停滞。
- **无内存泄漏**：请求体缓冲在数十万次大请求体后峰值**恒定**（仅个别 worker 出现一次
  2MB arena 扩展后稳定），流关闭后 `$stream['body']` 随流对象池正确回收。
- **请求体方向健壮性闭环**：与 §五 的「发送流控 + 大响应」互为镜像，HTTP/2 双向流控
  与内存生命周期在持续负载下均验证稳定、零泄漏。

### 5.2 混合负载长时压测（大请求体 + 大响应，双向流控同压）

§五 与 §5.1 分别验证了「发送流控 + 大响应」与「接收流控 + 大请求体」两个单向方向。
真实生产负载往往**双向同时压**：客户端一边灌大请求体、服务端一边回大响应。本项用
`benchmarks/h2-mixed-stress.sh` 驱动 `benchmarks/portable-server-post.php`
（设 `KODE_RESP_KB` 让 handler 读大请求体同时回大响应），把 recv 与 send 两个方向的
窗口流控同时推到极限，验证内存生命周期在双向缓冲下是否仍零泄漏。

实测（4 worker，100 连接，每连接最多 100 并发流，60s 持续，每请求 256 KB 请求体 + 256 KB 响应体）：

| 方向 | 吞吐 | 数据流量 | 请求数 | 失败 / 错误 / 超时 | 每 worker 内存峰值 | 峰值增长 |
|------|-----:|---------:|------:|:-----------------:|------------------:|:--------:|
| 双向（req 256KB + resp 256KB） | 10,697 req/s | ≈2.61 GB/s（170 GB 累计） | 641,843 | **0 / 0 / 0** | 42–46 MB | **0–2 MB（一次性 arena 扩展后恒定）** |

结论：
- **双向流控稳定**：60s、百万级字节在途下 **0 失败 / 0 错误 / 0 超时**，recv 与 send 两个
  窗口在持续相互背压下均正确回补 `WINDOW_UPDATE`，无任一方向耗尽导致的停滞。
- **内存零泄漏（双向）**：请求体缓冲（`recv` 方向）与响应体缓冲（`send` 方向）同压时，
  每个 worker 峰值仍**恒定**（仅个别 worker 出现一次 2MB arena 扩展后稳定），`$stream['body']` 与 `pending` 随流关闭正确回收。
- **健壮性闭环补全**：与 §五（发送）、§5.1（接收）共同构成 HTTP/2 双向流控 + 内存生命周期的
  完整长时压测覆盖——两个方向独立、组合均验证稳定、零泄漏。

### 5.3 发送路径优化的端到端收益（优化前后对拍）

§3.6 的微基准是同进程背靠背测的，真实链路还要叠加 socket、事件循环与对端。这里用**同一台机器、
同一脚本、同一参数**，唯一变量是 `Http2Session::flushPending()` 的新旧实现（用 `git stash` 切换），
跑 `h2-large-stress.sh` 直接对拍：

**1 MB 响应**（4 worker / 100 连接 / 4 线程 / 30s）：

| 指标 | 优化前 | 优化后 | 变化 |
|------|-------:|-------:|-----:|
| 吞吐 | 4,375 req/s | **11,942 req/s** | **2.73×** |
| 带宽 | 4.08 GB/s | **11.14 GB/s** | **2.73×** |
| 延迟 median | 21.76 ms | **7.20 ms** | **−66.9%** |
| 延迟 mean | 22.85 ms | 8.11 ms | −64.5% |
| p95 / p99 | 29.19 / 45.19 ms | 14.63 / 19.76 ms | −49.9% / −56.3% |
| 失败 / 错误 / 超时 | 0 / 0 / 0 | 0 / 0 / 0 | — |
| 每 worker 峰值内存 | 10–12 MB | 14–16 MB | 增长均为 **0 bytes** |

**256 KB 响应**（4 worker / 200 连接 / 4 线程 / 25s）：

| 指标 | 优化前 | 优化后 | 变化 |
|------|-------:|-------:|-----:|
| 吞吐 | 33,531 req/s | **44,584 req/s** | **1.33×** |
| 延迟 median | 5.64 ms | **3.74 ms** | **−33.7%** |

结论：
- **收益随响应体增大而放大**，与「平方 → 线性」的理论预期完全吻合：256KB 得 1.33×，1MB 得 2.73×。
- **延迟改善比吞吐更显著**：1MB 场景最小延迟从 14.84 ms 降到 0.517 ms——旧实现里每个大响应都要
  先扛完无谓 memcpy 才发得出第一帧，事件循环被单个响应长时间占住；新实现下首帧几乎立即发出。
- **内存不劣化**：256KB 场景峰值反而从 8MB 降到 6MB（少了逐帧重切产生的临时串）；
  1MB 场景峰值略高是因为吞吐 2.7 倍后在途响应更多，两者**增长均恒为 0**，无泄漏。

### 5.4 极端条件长时压测（8 worker / 512 连接 / 5 分钟，零泄漏验证）

§五 / §5.1 / §5.2 分别在 4 worker、200/100 连接、60s 下验证了发送流控、接收流控与双向流控的稳定性。
本项把条件推到极端——**8 worker、512 连接、300s 持续**——检验在远超常态的并发与在途字节下，
大响应缓冲与流对象池是否仍无泄漏、流控是否仍稳定。

实测（8 worker，512 连接，8 线程，300s 持续，256KB 响应体）：

| 指标 | 值 |
|------|----|
| 完成请求 | **9,842,160** |
| 吞吐 | **32,807 req/s**（7.65 GB/s，累计 2.30 TB） |
| 失败 / 错误 / 超时 | **0 / 0 / 0** |
| 2xx | 9,842,159（其余为 0） |
| 延迟 median / p95 / p99 | 11.49 ms / 36.32 ms / 54.45 ms |
| 每 worker 内存峰值 | 6.29 MB（5/8 worker）或 6.29 → 8.39 MB（3/8 worker，一次性 +2MB 后恒定） |
| 峰值增长 | **0 bytes（5/8）或一次性 2 MB 后恒定（3/8）** |

结论：
- **极端条件下零泄漏**：300s、近千万请求、512 连接持续灌大响应，每个 worker 的 PHP 峰值内存
  要么**完全恒定**（5/8 worker，增长 = 0 bytes），要么出现**一次 2MB arena 扩展后随即恒定**
  （3/8 worker），均为有界、一次性台阶，**没有任何随时间的无界增长**，
  大响应缓冲（`pending` / `body`）与流对象池在 8 worker 高并发下仍正确回收。
- **流控稳定**：9,842,160 请求 **0 失败 / 0 错误 / 0 超时**，说明服务端发送窗口随对端
  `WINDOW_UPDATE` 正确补还，8 worker 下无窗口耗尽导致的流停滞或连接级异常。
- **吞吐随 worker 数放大**：相较 §五 的 4 worker / 200 连接（29,660 req/s），本项 8 worker / 512 连接
  达 **32,807 req/s**（约 +10%），符合「吞吐随 worker 与连接数近线性放大」的预期，且零错误。
- 延迟在 512 连接高压下仍收敛（median 11.49ms、p99 54.45ms），无长尾失控。

> 注：极端并发下的延迟绝对值为「512 连接 × 多路复用流」的本地回环背压 artifact，非服务端缺陷；
> 健壮性信号（近千万请求 0 错误 / 0 超时 / 内存有界 plateau）才是重点。

## 六、异步 / 调度子系统微基准

事件循环、Promise 调度与 Crontab 不在请求热路径上，其收益是**最坏情况延迟、空闲 CPU 与分配压力**，
而非宏观 QPS。下列数字由 `benchmarks/async-bench.php` 与 `benchmarks/crontab-bench.php` 在
**v5.2.34（PHP 8.3.33）** 下测得；每项均带「旧版参考实现」对照，倍率为诚实可复现值。

### 6.1 Async 定时器：O(1) 提前返回

`processTimers()` 此前每 tick 全量扫描 `timers + intervals`（无论有无到期）。现用
`$nextTimerDue` 缓存最近到期点，`now < nextDue` 时 O(1) 直接返回。

| 场景 | 2000 个远未来定时器 × 20000 次 processTimers | 耗时 |
|------|--------------------------------------------:|-----:|
| 当前（O(1) 提前返回） | — | 0.902 ms |
| 旧版（每 tick 全量 O(N) 扫描，参考实现） | — | 275.543 ms |
| **加速比（旧 / 新）** | | **≈ 305×** |

> 收益随定时器数量线性放大：1k 定时器时空闲循环每 tick 从 1000 次比较降到 1 次比较。
> 同时 `Async::run()` 的休眠改为自适应 `min(堆顶剩余, 1ms)`，亚秒级定时器延迟精度提升、空闲 CPU 下降。

### 6.2 Promise 链路：subscribe 消除一次性 Promise

`doResolve` / `resolvePromise` 内部曾用 `$value->then(...)` 仅为登记回调，却多造一个立即丢弃的
Promise（连同其 executor 与两个 handler 闭包）。新增 `subscribe()` 只做登记分支。深链（每步返回新
Promise）分配由 **3K → 2K**（K=2000 实测 6001 → 4001），**减少 33.3%**。

### 6.3 Async::each / map 真实并发上限

`each()` 的 `$process` 闭包曾漏把 `$concurrency` 纳入 `use` 列表、循环写死 `10`，导致
`Async::map($items, $cb, 64)` 实际只有 10 路并发。已修复，实测峰值并发 == 请求值（如 8 即 8）。

### 6.4 Crontab 字段位掩码匹配

`searchNext` / `matchesDayOfMonthOrWeek` 的 `in_array` 线性扫描改为 64 位位掩码
`(($mask >> $v) & 1)`。瓶颈在 `getdate()`，故倍率温和，但在每秒级密集表达式上最明显：

| 表达式 | 位掩码 | in_array（参考） | 加速比 |
|--------|-------:|----------------:|------:|
| `* * * * *`（每秒） | 7.24 ms | 9.85 ms | 1.36× |
| `*/5 * * * * *` | 7.36 ms | 8.58 ms | 1.17× |
| `0 * * * * *`（每小时第 0 秒） | 39.2 ms | 47.8 ms | 1.22× |
| `*/15 * * * *` | 108.4 ms | 112.3 ms | 1.04× |
| `0 0 * * 1-5` | 192.8 ms | 194.5 ms | 1.01× |
| `0 0 13 * 5`（POSIX 并集） | 36.4 ms | 37.2 ms | 1.02× |

> 位掩码的主价值是**零线性扫描 + 无数组分配**，且正确性由「位掩码 vs 暴力逐秒扫描」等价测试守护
> （`CrontabTest::testBitmaskMatchesBruteForceOverHorizon`，覆盖 POSIX 并集、2 月 30 日等语义）。

### 6.5 Timer::parseCronNext：字段映射修正 + 位掩码缓存

**正确性修复**：旧实现把 5 段表达式整体偏移了一位 —— 以 `$parts[4]/[3]/[2]/[1]`
依次匹配 `wday / mday / hours / minutes`，**分钟字段 `$parts[0]` 被完全忽略、月份字段被当作日使用**。
现按标准 cron 语义正确映射到 `(minute, hour, mday, month, wday)`，
并对全部五段做 AND 匹配。等价性由 `TimerTest::testParseCronNextMatchesReferenceImplementation` 守护。

**性能优化**：旧实现每轮扫描都对 5 段重新做字符串解析；现于每条表达式首次计算时用 `matchCronPart`
枚举各字段定义域一次性求并集位掩码并缓存（`self::$cronMaskCache`，上限 256 条），之后每个候选时间只需 5 次位运算。

性能（复杂表达式 `1-30/5 1-12/2 1,15 * 1-5`，2000 次解析、掩码缓存热路径）：

| 实现 | 耗时 |
|------|-----:|
| 新（位掩码缓存热路径） | 9742 ms |
| 旧（逐轮字符串解析） | 20260 ms |
| **加速比** | **≈ 2.1×** |

### 6.6 Async::queueMicrotask：元组参数消除闭包分配

`Async::queueMicrotask(callable $cb, ...$args)` 现以 `[$cb, $args]` 元组入队、`runMicrotasks`
以 `$cb(...$args)` 调用；`Promise` 决议热路径上 6 处 `fn() => $cb($v)` 闭包包裹改为直接
`queueMicrotask($cb, $v)`。不定参时行为不变（向后兼容）。

20 万次微任务分发（本机实测，闭包分配受 GC 影响波动较大，方向稳定）：

| 风格 | 耗时 | 峰值内存增量 |
|------|-----:|-------------:|
| 旧（`fn() => $cb($v)` 闭包包裹） | 73.413 ms | +108 MB |
| 新（`queueMicrotask($cb, $v)` 元组） | 46.188 ms | ≈ 0 |
| **加速比** | **≈ 1.6×（多次实测区间 1.6×–3.0×）** | **闭包分配几乎归零** |

> 闭包分配减少直接转化为 GC 压力下降；长 `Promise` 链、高并发异步、以及 `await` 密集场景下收益放大。

### 6.7 ProcessMonitor：进程级常量缓存

`getCpuCount()`（核数）与 `getClockTicks()`（时钟滴答）在进程生命周期内恒定，旧实现每次
`getProcessCpu()` 都重新 `shell_exec('nproc')` / `posix_sysconf`，在 `checkAll()` 多 pid 轮询下
产生大量冗余系统调用。现改为懒初始化静态缓存，命中后零系统调用。由
`ProcessMonitorTest::testCpuConstantsAreStableAndCached` 守护返回值契约与幂等性。

## 七、默认事件循环 SelectLoop 惰性 prune

SelectLoop 是未安装 ext-event / ext-ev 平台（非常多环境）的兜底多路复用器，其每 tick 效率直接决定兜底 QPS。

### 7.1 改动

旧实现在**每次 `select()` 前**都全量 `pruneInvalidStreams()`（遍历所有读写流做 `is_resource` 检查），即每 tick 一次 O(N) 扫描。
现改为**惰性 prune**：正常 tick 零扫描直接 `stream_select`；仅当流被外部 `fclose` 却未调用 `off*` 导致抛 `ValueError` 时，
才 `catch` 一次、剔除失效流、重建集合并重试一次。稳态每 tick 用户态开销从 O(N) 降为 O(1)。

### 7.2 微基准（benchmarks/selectloop-bench.php）

模拟 N=2000 并发连接、每轮 K=100000 tick：

| 路径 | 每 tick 用户态扫描 | 每 10万 tick 累计 |
|------|-------------------|------------------|
| 旧（每 tick 全量 O(N) 扫描）参考 | ≈ 0.01396 ms | ≈ 1395.6 ms |
| 新（惰性 prune，零扫描） | 0 ms | 50.5 ms（仅 select 本身） |

新实现在 4 个真实低 fd 流上实跑 K 次 `select(0)`：流集合完整保留（4/4）、零异常穿透。

**结论**：稳态每 tick 省掉一次 N 元 `is_resource` 扫描——连接越多该扫描越贵，兜底事件循环在无效流不出现的常态下尾延迟与 CPU 占用双降；仅在「外部关闭未 off」这一异常路径上多付出一次 prune，符合 fail-soft 设计。

### 7.3 回归守卫

`SelectLoopTest::testSelectLazilyPrunesExternallyClosedStream`（反射驱动私有 `select()`，断言「不抛 + 失效流被惰性剔除」）、`testSelectKeepsValidStreamsAcrossManyTicks`（200 次 tick 后有效流完整保留，反向守卫零扫描路径不误伤）。既有 `testPrunesClosedStreamInsteadOfSpinning` 仍通过。

### 7.4 FD_SETSIZE 状态的健壮暴露

`stream_select` 底层 bitset 受 `FD_SETSIZE`（通常 1024）限制：一旦连接数把 fd 推到 ≥1024，select 会失败并退化为每 tick 空转。这是**平台限制，不是代码缺陷**。

该状态在**注册期**（`guardFdLimit`）与**运行期 select 失败**两处都会暴露，并经统一 `fdSetSizeWarned` 标志保证**全生命周期只告警一次**：

```
SelectLoop: 检测到 fd >= 1024 (FD_SETSIZE)，stream_select 无法安全监听该流，
多路复用将退化为每 tick 空转。请安装 ext-event / ext-ev 切换到 C 层多路复用以解除连接数上限。
```

运行期用 `hasFdAtOrAboveSetSize()` 精准判定「集合里确含 ≥1024 的 fd」才告警，避免 EINTR 等误报。仅告警、不抛、不刷屏；若要真正解除连接数上限，仍须切到 ext-event/ext-ev 的 C 层多路复用。契约由 `SelectLoopTest::testFdSetSizeWarningFiresExactlyOnce` 守护。

## 使用方向（选型建议）

1. **受限 / 容器 / 无扩展环境**：不装 swoole/workerman 扩展即可跑起完整 HTTP + WebSocket + HTTP/2 服务——选 **native**。
2. **现代 PHP 8.3+ 项目**：枚举、只读属性、Fibers 等，代码即服务器，调试直观——选 **native**。
3. **需要 HTTP/2（h2c）**：gRPC 网关、前端静态资源、内部多路复用 RPC——**只有 native 默认即开**，明文即可。
4. **极致单连接吞吐 / 协程**：高并发 I/O 密集且能装 C 扩展——选 **swoole**。
5. **已深度使用 Workerman 生态**：业务已绑定 Workerman 组件——选 **workerman**（native 可零改动切换做对标）。
6. **自建 PaaS / 嵌入式 / 教学**：一份纯 PHP 源码，改得动、读得懂——选 **native**。

> 一句话：本项目的定位本就不是「在压榨极限吞吐上赢 C 扩展」，而是强在「零安装即得、PHP 8.3+ 现代写法、
> HTTP/2 开箱即用且自带 DoS 防护、协议与关闭更规范、代码可读可测」：在绝大多数业务服务的吞吐区间内，
> 它与 swoole / workerman **同量级**，并在请求热路径 CPU 上稳定领先（微基准方向 100% 全胜）；
> HTTP/2 请求热路径经四层纯函数缓存（编码 5.7× / 整头 3.4× / 响应整块 2.2× / 解码 1.93×）、
> 解码主循环内联（1.47×）、解码字符串读取内联（1.22×）多重优化，叠加发送路径去平方（1MB 端到端 2.73×、延迟 −67%），
> 这些收益全部落在 PHP 用户态热路径上，是纯函数缓存 / 主循环内联带来的真实、可复现提速；
> h2c 与 h1.1 的吞吐差距稳定在协议固有代价区间，与运行时选型无关。

## 怎么复现

```bash
# 需要 wrk 与 h2load：brew install wrk nghttp2

# 三运行时吞吐对比（HTTP/1.1，wrk）
bash benchmarks/runtime-bench.sh 4 12 200 4

# HTTP/2 同等条件吞吐：同一 native 服务、同时刻 h2c vs h1.1
bash benchmarks/h2-bench.sh 4 19301

# 纯 CPU 热路径微基准（无需 wrk）
php benchmarks/hotpath-micro.php

# HTTP/2 响应热路径微基准（HPACK 编码 + feed/respond）
php benchmarks/hotpath-h2.php

# HTTP/2 解码热点拆分（Huffman 占比定位）
php benchmarks/h2-decode-bench.php

# 发送路径微基准：大响应切帧 + 多流 WINDOW_UPDATE 空转（§3.6）
php -d memory_limit=1G benchmarks/h2-flush-bench.php 200

# 发送路径线格式对拍：247 组场景的 SHA-256 摘要，改写前后必须完全一致
php benchmarks/h2-flush-equiv.php | tail -1

# feed/respond 拆分（解码 vs 编码耗时占比）
php benchmarks/h2-split.php

# 纯函数组件耗时拆解（Frame 编解码 / HPACK 编解码各自占比）
php benchmarks/h2-components.php

# 大响应长时压测（发送流控 + 大响应缓冲，健壮性 / 零泄漏）
bash benchmarks/h2-large-stress.sh 4 19310 256 60 200 4

# 极端条件长时压测（8 worker / 512 连接 / 5 分钟，验证零泄漏与流控稳定，§5.4）
bash benchmarks/h2-large-stress.sh 8 19310 256 300 512 8 20000

# 带 body 的 POST 长时压测（接收流控 + 请求体缓冲，健壮性 / 零泄漏）
bash benchmarks/h2-post-stress.sh 4 19311 512 60 100 4 100

# 混合负载长时压测（大请求体 + 大响应，双向流控同压，健壮性 / 零泄漏）
bash benchmarks/h2-mixed-stress.sh 4 19311 256 256 60 100 4 100

# 慢读防护（滴流型 Slowloris）为 serve() 的可选参数：readTimeout（秒，默认 0 关闭）。
# 例：Kode::serve('http://0.0.0.0:8080', ['readTimeout' => 5], 'native')
# 与 MAX_HEADER_BUFFER(64KB 头部体积上限) 形成「体积 + 时间」双重防护。
```

- `benchmarks/portable-server.php`：跨运行时通用的服务脚本（`Kode::serve(..., 'native'|'swoole'|'workerman')`）。
  不显式传 `reusePort` 时走运行时的平台自适应默认。可用 `REUSE_PORT=0|1` 环境变量覆盖做 A/B。
- 运行期产物（`bench-result.txt`、`compare-result.txt`、`workerman.log` 等）已加入 `.gitignore`，不入库。
- `benchmarks/portable-server-large.php` / `benchmarks/h2-large-stress.sh`：大响应长时压测，验证
  **发送流控**与响应缓冲零泄漏（§五）。
- `benchmarks/portable-server-post.php` / `benchmarks/h2-post-stress.sh`：带 body 的 POST 长时压测，
  验证**接收流控**（`recv` 窗口 + `WINDOW_UPDATE`）与请求体缓冲零泄漏（§5.1）。
  `portable-server-post.php` 另支持 `KODE_RESP_KB` 环境变量回大响应，配合 `h2-mixed-stress.sh`
  做**双向混合负载**压测（§5.2）。
