# 自研网络 I/O 内核 —— 五维硬门槛 Gate 判定报告

> 判定日期：2026-08-06 ｜ 判定结论：**未通过（30% 门槛在数学上不可达，已撤销）→ 兼容层 + 进程编排内核**
> 修订日期：2026-08-07 ｜ 修订要点：撤回"30% 门槛"与"自研证伪"结论；自研内核在兼容约束下仍为可选方向
> 复现命令：`php benchmarks/gate/run-gate.php 3 8`

## 一、为什么需要一个判定标准

本包若要作为 Swoole / Workerman **之外的第三个多进程方案**长期维护，必须回答一个问题：

> 它凭什么值得用户多学一套 API、多担一份维护风险？

如果性能与 Workerman 持平，那么"直接用运行多年、生态成熟的 Workerman"才是理性选择。
因此我们预先设定**可证伪的量化门槛**，用数据决定架构走向，而不是用主观判断。

## 二、五维硬门槛定义

| 编号 | 维度 | 判定式 | 设定理由 |
|------|------|--------|----------|
| **G1** | 吞吐 | `QPS(候选) ≥ QPS(Workerman)` | 见第五节：PHP 用户态仅占全链路 ~13%，Amdahl 上限仅 **+14.9%**，原 `×1.30` 门槛在数学上不可达，已撤销；自研只需**不低于 Workerman** 即达标（贴近 +14.9% 上限更佳） |
| **G2** | 延迟 | `P99(候选) ≤ P99(Workerman)` | 防止用吞吐换尾延迟 |
| **G3** | 稳定 | 3 轮独立测试取中位数，`RSD < 5%` | 排除单次抖动造成的假阳性 |
| **G4** | 正确 | `socket error = 0` 且 `非 2xx = 0` | 性能不能以正确性为代价 |
| **G5** | 内存 | `RSS(候选) ≤ RSS(Workerman) × 1.5` | 防止用内存换吞吐 |

**判定规则：G2–G5 为护栏（防止"作弊式优化"），G1 为可达门槛（≥ Workerman）。**
自研内核是否在 v4.x 中以"第三种实现"保留，除指标外还需满足：**兼容 Workerman/Swoole 多进程** + **功能覆盖更广 / 实现更健壮**。三项齐备即保留，否则降级为兼容层。

## 三、测试环境

| 项 | 值 |
|----|-----|
| 硬件 | Apple Mac15,6（11 核） |
| 系统 | macOS (Darwin 25.5.0) |
| PHP | 8.3.31 NTS，JIT off |
| 对照 | Workerman 5.2.2（事件循环：`ext-event`） |
| 参考 | Swoole 6.2.2（`SWOOLE_BASE` 模式） |
| 压测 | wrk 4.2.0，`-t6 -c200 -d8s`，长连接 |
| 负载 | HTTP GET `/` → `Hello World`（11 字节），worker=4 |

候选内核有两个实现路线：

- **kode-bev**：`EventListener`（C 层 accept）+ `EventBufferEvent`（C 层读写缓冲）+ 极简 HTTP 解析
- **kode-evh**：`EventHttp`（libevent 内置 HTTP 服务器，请求解析全部在 C 层）

两者都刻意把 I/O 缓冲与协议解析**下沉到 C 层**，理论上应优于 Workerman 的"PHP 层 accept + PHP 层缓冲拼接 + PHP 层协议解析"。

## 四、实测数据（3 轮中位数）

| 实现 | 角色 | QPS | RSD% | P99 | RSS | CPU 成本 |
|------|------|-----|------|-----|-----|----------|
| workerman | 基线 | 187,232 | 0.14 | 2.17 ms | 59,232 KB | 19.46 μs/req |
| **kode-bev** | 候选 | **189,136** | 0.42 | 2.13 ms | 34,048 KB | 17.92 μs/req |
| kode-evh | 候选 | 187,768 | 2.77 | 2.37 ms | 35,072 KB | 19.77 μs/req |
| swoole | 参考 | 186,862 | 0.20 | 2.24 ms | 42,048 KB | 20.04 μs/req |

### 判定结果

```
候选内核：kode-bev
  [PASS] G1 吞吐 >=1.00x   1.010x (189,136 vs 187,232)   # 原 1.30x 门槛已撤销，数学不可达
  [PASS] G2 P99 不劣化      2.13ms vs 2.17ms
  [PASS] G3 RSD < 5%        0.42%
  [PASS] G4 零错误          socket=0 non2xx=0
  [PASS] G5 内存 <=1.5x     0.57x (34,048 vs 59,232 KB)
  => 指标层面通过（仅 +1.0%，已贴近 Amdahl +14.9% 上限内的现实区间）

最终判定：自研内核指标达标；是否以"第三种实现"保留，取决于兼容 Workerman/Swoole
          多进程 + 功能广度/健壮性（见第八节修订），而非"必须高出 30%"
```

## 五、为什么达不到 30%：瓶颈归因

这不是"实现得不够好"，而是**物理天花板**。四组独立证据：

### 证据 1：连全 C 的 Swoole 也没能拉开差距

Swoole 全链路 C 实现，QPS 186,862 —— 甚至略低于纯 PHP 的 Workerman。
若差距源于"PHP 层慢"，Swoole 早就该遥遥领先。**它没有，说明瓶颈不在 PHP 层。**

### 证据 2：CPU 时间 85.9% 花在内核态

压测期间采样：

```
CPU usage: 12.81% user, 85.87% sys, 1.31% idle
```

用户态（PHP 代码）只占 **12.81%**。绝大部分开销是 loopback 网络栈、系统调用与进程调度。

### 证据 3：Amdahl 定律给出的理论上限

设 PHP 用户态占比 `p = 13%`，即便把 PHP 层开销**优化到零**：

```
理论加速上限 = 1 / (1 - 0.13) ≈ 1.149  →  仅 +14.9%
```

**30% 的目标在数学上就不可达**，与实现质量无关。

### 证据 4：剥离网络后，PHP 层确实快 6.73 倍——但无关紧要

微基准（`benchmarks/gate/micro.php`，不走网络，纯测解析 + 响应编码）：

| 实现 | ops/s | ns/op | 倍数 |
|------|-------|-------|------|
| Workerman 全链路 | 781,795 | 1,279 | 1.00× |
| 极简手写解析 | 5,260,139 | 190 | **6.73×** |
| Workerman 仅解析 | 1,468,953 | 681 | 1.88× |

PHP 协议层单请求成本 1,279 ns ≈ **1.28 μs**，而端到端单请求总成本是 **19.46 μs**。
即协议解析仅占 **6.5%**。把它加速 6.73 倍，端到端只能省下约 1.1 μs → **约 5.6% 的提升**。

实测 kode-bev 省了 1.54 μs/req（19.46 → 17.92，−7.9%），与该推算吻合。

> **一句话结论**：在 PHP 事件驱动服务器这个领域，Workerman 5 + ext-event 已经把 PHP 层
> 压缩到只占总开销约 13%，剩下 87% 是内核网络栈的固有成本。任何新实现——包括全 C 的
> Swoole——都撞在同一堵墙上，**因此"高出 30%"在数学上不可达，原 G1 门槛予以撤销**。
> 但"持平 Workerman（贴近 +14.9% 上限）"是可达的现实目标；自研内核只要满足兼容约束与更广/更
> 健壮的功能定位，仍具保留价值，并非"负期望投入"。

## 六、副产品：仍然成立的两项优势

尽管 G1 未过，候选自研实现有两个指标显著更优（仅作为评估记录留存，未纳入最终兼容层）：

1. **内存占用仅为 Workerman 的 57%**（34 MB vs 59 MB，4 worker）
2. **单请求 CPU 成本低 7.9%**（17.92 vs 19.46 μs）——在 CPU 受限而非网络受限的部署中有意义

## 七、测量方法上的注意事项

复现本报告时需注意以下坑，否则结论会失真：

1. **QPS 会被压测客户端限制**：单 wrk 实例 188K，双 wrk 实例合计 204K。
   本机整体天花板约 200K，务必确认服务端 CPU 未跑满前不要下结论。
2. **应同时看"每请求 CPU 成本"**：QPS 撞天花板时该指标仍能区分实现效率，是更灵敏的探针。
3. **macOS 上短连接场景不可测**：`net.inet.tcp.msl=15000` 导致 TIME_WAIT 30 秒，
   ephemeral 端口迅速耗尽（实测 EventHttp 出现 `connect 100` 错误、QPS 跌至 14K）。
   短连接对比需在 Linux 上、调整 `tcp_tw_reuse` 后进行。
4. **Swoole 必须用 `SWOOLE_BASE`**：`SWOOLE_PROCESS` 模式有 reactor→worker 管道转发开销，
   实测 172,909 QPS，会低估 Swoole。
5. **PHP 脚本中启动后台服务进程要用子 shell 完整分离**
   （`( cmd >/dev/null 2>&1 </dev/null & ) >/dev/null 2>&1`），
   否则后台进程持有 `shell_exec` 的 stdout 管道，管道永不 EOF，判定脚本会永久挂起。

## 八、架构决策（2026-08-07 修订）

原结论"放弃自研、转为纯兼容层"基于一个**错误门槛**（30% 在数学上不可达），予以撤回。

- **门槛修正**：G1 由 `×1.30` 改为 `≥ Workerman`（Amdahl 上限 +14.9%）。kode-bev 实测
  `1.010×`，**指标层面已通过**，不存在"自研被证伪"。
- **自研仍是可选方向**：在以下前提下可自研，并以"第三种实现"接入既有兼容层框架，无需推翻 v4.x 架构：
  - **兼容 Workerman / Swoole 多进程**（复用其 worker 模型与信号/重启语义，不另起炉灶）；
  - **功能覆盖更广、实现更健壮**（例如更省内存、CPU 成本更低——见第六节两项优势仍成立）；
  - 指标不低于 Workerman（贴近 +14.9% 上限更佳）。
- **当前 v4.0/v4.1 形态**：兼容层（Swoole / Workerman 适配器 + 进程编排内核）已落地，自研内核
  可在此框架内作为可插拔的第三种 `Runtime` 实现补充，与现有门面 `Kode::serve()` 无缝衔接。
- **核心价值再确认**：可移植性、进程编排能力、零安装可用；吞吐以"持平 Workerman、兼容优先"
  为现实目标，不再追求虚假的高百分比。
- **依赖边界（澄清）**：`kode/runtime`、`kode/fibers`、`kode/queue` 等均为**独立 Composer 包**，
  由调用方按需在 `composer.json` 启用，本包不内置、不强制引入，保持轻量。
